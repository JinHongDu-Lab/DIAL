# Operating Guidelines

This study measures **position effects only** — every collected condition is
anonymous (assistant labels never disclose the source model name). Like
`arena_33k`, the `anonymity` factor declares a single fixed level, so the
condition grid is 2 cells (`original_anonymous`, `swapped_anonymous`), not a
full 2×2. Identity-contrast metrics (`identity_flip_rate`,
`identity_*_probability_delta`) and the named/anonymous `position_*_named`
metrics are therefore always unavailable (`NA`) in this study's reports —
that is expected, not an error.

## Dataset scale and provenance

The dataset (`../../data/pandalm_prepared.parquet`, generated by
`../../scripts/prepare_dataset.py` from the raw
`../../data/pandalm_testset_v1_raw.parquet` — see `../../data/README.md` for
full download/regeneration instructions) has **945 rows**, smaller than
`arena_33k`'s 7,738. PandaLM's human test set covers only **5 candidate
models** (`bloom-7b`, `cerebras-gpt-6.7B`, `llama-7b`, `opt-7b`,
`pythia-6.9b` — all similar-scale 2023 open-source 7B checkpoints, no
frontier/API models), with all 10 pairwise combinations represented. Each
example was rated by **3 independent human annotators**; `winner` is the
majority vote across them (falling back to `tie` on a non-majority split,
which did not occur in the 2026-08-07 download — every example had either a
unanimous or a clean 2-1 majority).

This is not a JA-ranking-framework dataset — PandaLM has no corresponding
file in `TanXZfra/Judge-Aware-Ranking-Framework-for-LLMs`, so there is no
JA-ranking LLM-judge-verdict comparison available for this study (unlike
`arena_33k`). The value here is PandaLM's own genuine multi-annotator human
labels with explicit model identity on both sides — see
`plan/2026-08-07-add-mtbench-and-evaluate-preference-datasets.md` for why
this dataset was chosen over HH-RLHF (no model-identity metadata) and OASST1
(assistant replies are human-written, not LLM output).

## Running the study

Use **Validate only — no API calls** to check the dataset, manifest, prompt
templates, judge configuration, and every selected condition without
requiring credentials or contacting a provider.

Use **Run experiment — uses API** only after validation. It calls each
selected judge that has at least one available configured credential. Judges
whose credentials are entirely absent are recorded and skipped; an invalid
present credential is a runtime provider error.

Run names identify audit records under `logs/runs/<run>/`. Reuse a name only
with the same dataset, prompts, judges, inference profiles, record limit,
and condition grid. Successful responses are shared and deduplicated under
`results/<judge>/`; cumulative reports are written to `reports/<judge>/`.
Run-specific errors, status, usage, effective settings, and one combined
all-judge summary remain under the run log directory.

Keep credentials in environment variables or the ignored `.env` file. Never
put keys in this manifest, prompts, output, or reports.

## Judge panel

The manifest loads `configs/apis.json` for infrastructure and the **shared**
`../../../arena_140k/studies/position_and_anonymity/judges.json` catalog for
scientific profiles — this study does not maintain its own judge catalog.
Judge aliases name their reasoning behavior (`direct`, `low`, or `thinking`);
do not reuse an alias for another inference profile.

This study reuses `arena_33k`'s exact 24-judge, no-`hku-*` panel (see
`plan/2026-08-07-arena-33k-candidate-models-vs-judge-panel.md`): free local
Ollama judges for every company that has an open-weight option, falling back
to each provider's cheapest first-party batch model only for OpenAI, Google,
and Anthropic. Where a family ships multiple sizes and/or a reasoning
toggle (DeepSeek-R1, Qwen3, GLM-4.7-Flash, Phi4, Gemma), every practical
local variant is included on purpose, to let analysis compare
position/alignment bias across model size and reasoning ability within a
family, not just across companies. All Ollama judges require a running
loopback server and the model tags pulled locally; no API key. Treat the
local tag, quantization, and digest as part of the scientific judge
identity; do not combine their cached results with a cloud deployment of the
same base model.

The complete factor grid (both declared conditions) supports the paired
position causal-effect estimate. A partial grid is valid and receives the
same descriptive per-condition report, but its factorial section lists the
missing cells and remains unavailable. Within a judge, the runner schedules
selected conditions for each record/repetition as one bundle. Thus original
and swapped positions are queried consecutively for that unit, while
different records may remain concurrent.

Successful live results enter the canonical judge file and a rebuildable
lookup index, so later compatible ranges skip them without another API call.
Validation ignores and does not update shared results. The dashboard's
overall progress describes the canonical manifest workload, independent of
the selected run log.

This study's prompt offers **3** verdict options (`a`/`b`/`c` — no `d: both
bad`), same as `arena_33k`. A prompt edit defines a new scientific result
generation. Before such an edit, use `causal-judge-archive --study study.toml
--label <label>` to preserve cumulative results, reports, configuration,
prompts, and cache under `logs/archives/`. Archived run names remain
read-only under `logs/runs/` but are excluded from the active Web UI through
`logs/state/generation.json`.
